# Протокол PC Dock, версия 2 (черновик)

Статус: **черновик для ревью**, 2026-10-27. Реализации пока нет. Текущая реализация в `app-screencast`/`viewer` говорит на протоколе v1 (см. конец документа).

Протокол публичный: приёмником на телефоне может быть любое приложение, а хостом на ПК любая библиотека, которые его соблюдают.

## 1. Слои

```
Команды ввода (курсор, касания, клавиши)  ← абстракция SDK, см. §8
            │
   Поток пакетов (этот документ, §3–§7)   ← байтовый поток между хостом и телефоном
            │
   Транспорт: USB bulk (AOA), adb-туннель, сокет
            │
   Плоскость управления AOA (§2): handshake и HID — вне потока пакетов
```

Поток пакетов не зависит от транспорта: ему нужен надёжный упорядоченный двунаправленный байтовый канал.
Все числа в **big-endian**. Строки — UTF-8.

## 2. Плоскость управления AOA (вне потока)

Выполняется хостом через USB control transfer на устройстве (Android Open Accessory, протокол версии ≥ 2).

| Запрос | Код | Назначение |
|---|---|---|
| `GET_PROTOCOL` | 51 | версия AOA на телефоне (нужна ≥ 2 для HID) |
| `SEND_STRING` | 52 | индекс 0..5: производитель, модель, описание, версия, URI, серийник |
| `START` | 53 | перейти в режим аксессуара (телефон переподключается как `18d1:2d00`/`2d01`) |
| `REGISTER_HID` | 54 | `wValue` = id устройства, `wIndex` = длина дескриптора |
| `UNREGISTER_HID` | 55 | `wValue` = id |
| `SET_HID_REPORT_DESC` | 56 | `wValue` = id, `wIndex` = смещение, данные ≤ 4096 байт |
| `SEND_HID_EVENT` | 57 | `wValue` = id, данные = отчёт |

Настраивается пользователем: все шесть строк (должны совпадать с фильтром приложения-приёмника), идентификаторы HID, дескрипторы HID.
**Не настраивается** (выбирает Android): имя и VID/PID виртуальных HID.

Данные потока идут по bulk-интерфейсу accessory (в режиме аксессуара это интерфейс 0).

## 3. Формат пакета

```
смещение  размер  поле
0         2       magic = 0x50 0x44 ("PD")
2         1       type
3         1       flags (смысл зависит от type, неиспользуемые биты = 0)
4         4       length — длина payload в байтах (≤ 16 777 216)
8         length  payload
```

- Получатель **обязан пропускать** пакеты неизвестного `type` (читает `length` и отбрасывает).
- **Ресинхронизация** при ошибке (неверный magic или недопустимая длина): искать следующее `PD`, начиная со второго байта; кандидат принимается, если за ним (когда данных достаточно) идёт ещё один корректный заголовок.
- v1 отличается тем, что поток начинается с длины, а у кадра < 16 МБ первый байт равен 0x00, а у v2 это `0x50`. По первому байту реализация может отличить версии.

## 4. Типы пакетов

| type | Имя | Направление | Описание |
|---|---|---|---|
| 0x01 | `HELLO` | оба | открытие сессии, версия и возможности |
| 0x02 | `PING` | хост → телефон | keep-alive (8 байт nonce) |
| 0x03 | `PONG` | телефон → хост | ответ, тот же nonce |
| 0x10 | `DISPLAY_INFO` | телефон → хост | размеры, плотность, поворот |
| 0x11 | `VIDEO_FRAME` | телефон → хост | кадр экрана |
| 0x12 | `VIDEO_CONFIG` | телефон → хост | параметры кодека (SPS/PPS), зарезервировано для H.264 |
| 0x20 | `AUDIO_CONFIG` | телефон → хост | формат звука |
| 0x21 | `AUDIO_FRAME` | телефон → хост | звук |
| 0x30–0x37 | `INPUT_*` | хост → телефон | ввод для бэкендов без HID (ADB, root), зарезервировано |
| 0x40 | `REQUEST_FRAME` | хост → телефон | немедленно прислать кадр |
| 0x41 | `SET_STREAM` | хост → телефон | настройки потока |
| 0x42 | `WAKE` | хост → телефон | включить экран на минуту (разблокировка вручную) |
| 0x50 | `STATUS` | телефон → хост | событие |
| 0x7F | `ERROR` | оба | ошибка |

## 5. Сессия

Сессию начинает **хост**, а не телефон. Телефон до первого `HELLO` от хоста ничего не шлёт.

1. Хост → `HELLO`.
2. Телефон → `HELLO` (выбранная версия и возможности), затем `DISPLAY_INFO`, затем `VIDEO_FRAME` с текущим содержимым экрана (тот же последний кадр, если экран статичен).
3. Дальше поток: `VIDEO_FRAME` (и `AUDIO_*`, если включено) от телефона, `PING`/`SET_STREAM`/`REQUEST_FRAME` от хоста.

**Любой новый `HELLO` от хоста перезапускает сессию** (состояние сбрасывается, шаг 2 повторяется). Благодаря этому перезапуск ПК-стороны при живом соединении не требует сброса USB, и экран не остаётся чёрным.

### HELLO (0x01), payload

```
u16  version_max     максимальная версия, которую понимает отправитель
u16  version_min     минимальная
u32  capabilities    битовая маска, см. ниже
u8   role            0 = хост (ПК), 1 = телефон
u8   name_len
...  name            имя реализации, например "pcdock-android/1.0"
```

Версия сессии = `min(version_max)` обеих сторон при условии `>= max(version_min)`; иначе `ERROR` (код 1) и закрытие.
`capabilities` телефона: что он умеет; хоста: что он готов принимать. Сессия использует пересечение.

| бит | Возможность |
|---|---|
| 0 | видео JPEG |
| 1 | видео H.264 |
| 2 | звук PCM s16le |
| 3 | звук Opus |
| 4 | поворот экрана (`DISPLAY_INFO` меняется на лету) |
| 5 | ввод внутри потока (`INPUT_*`) |
| 6–31 | зарезервировано |

### PING/PONG

`PING` хост шлёт каждые 2 с (payload: `u64 nonce`), `PONG` возвращает тот же nonce.
Телефон считает сессию мёртвой, если 6 с нет ни одного пакета от хоста: переходит в ожидание и перестаёт слать медиа.
Хост считает телефон недоступным, если 6 с нет ни одного пакета от него (при статичном экране `PONG` служит признаком жизни).

### STATUS (0x50), payload

```
u16  code      код события (значения задаёт реализация приёмника)
...  detail    UTF-8 до конца payload
```

Примеры кодов для приёмника на Android: 1 = трансляция остановлена пользователем или системой, 2 = звук недоступен.

### Ошибки

`ERROR (0x7F)`: `u16 code`, затем сообщение UTF-8 до конца payload.
Коды: 1 версия не поддерживается, 2 некорректный пакет, 3 внутренняя ошибка.

## 6. Видео и экран

### DISPLAY_INFO (0x10), payload (u16, если не сказано иное)

```
stream_width, stream_height   размер кадров, которые пойдут дальше
screen_width, screen_height   реальный размер экрана телефона в пикселях в текущей ориентации
density_dpi
u8 rotation                   0, 1, 2, 3 = поворот 0°, 90°, 180°, 270° (как Surface.ROTATION_*)
u8 reserved
```

Отправляется после `HELLO`, а затем **при любом изменении** размера или поворота, до первого кадра с новым размером.
Кадры после `DISPLAY_INFO` имеют новый размер, кадры до него старый.
Размер кадра **всегда** соответствует ориентации, в которой пользователь видит экран (картинка не требует поворота на стороне хоста). `rotation` нужен хосту только для информации и для пересчёта ввода.

Хост считает масштаб как `screen / stream`, а не берёт константу.

### VIDEO_FRAME (0x11)

```
flags: бит 0 = ключевой кадр (для JPEG всегда 1)
payload:
  u8   codec        1 = JPEG, 2 = H.264 (Annex B)
  u64  pts_us       время кадра, монотонные микросекунды часов телефона
  ...  data
```

Кадры JPEG независимы, потеря любого не ломает поток. Для H.264 после потери нужен `REQUEST_FRAME` и ключевой кадр (зарезервировано).

### REQUEST_FRAME (0x40)

Пустой payload. Телефон присылает текущее содержимое экрана, даже если оно не менялось.

### SET_STREAM (0x41), payload

```
u8   flags          бит 0 = видео включено, бит 1 = звук включён
u16  max_width      0 = по умолчанию
u16  max_height     0 = по умолчанию
u8   jpeg_quality   0 = по умолчанию, 1..100
u8   max_fps        0 = без ограничения
```

После применения телефон присылает `DISPLAY_INFO` с итоговым размером.

### WAKE (0x42)

Пустой payload. Телефон включает экран на минуту (чтобы ввести PIN вручную). Если экран
уже включён — ничего не делает. Постоянно экран не держится (бережём батарею).

## 7. Звук

Захват звука приложений на телефоне (`AudioPlaybackCapture`, Android 10+), через ту же проекцию. Приложения могут запретить захват своего звука.

- `AUDIO_CONFIG (0x20)`: `u8 codec` (1 = PCM s16le, 2 = Opus), `u32 sample_rate`, `u8 channels`. Шлётся перед первым звуком и при изменении.
- `AUDIO_FRAME (0x21)`: `u64 pts_us`, затем данные.

## 8. Модель ввода (абстракция SDK)

Эти команды фронтенд отправляет в SDK; как они доходят до телефона, решает бэкенд. В AOA-бэкенде это HID-отчёты по control transfer (§2), в ADB/root-бэкендах пакеты `INPUT_*`.

Координаты **нормированные** `0.0..1.0` относительно текущего отображаемого экрана (с учётом поворота).

| Команда | Параметры |
|---|---|
| `device_enable` | `kind` ∈ {`touch`, `mouse`, `keyboard`}, `enabled` |
| `touch` | `id` (u8, номер пальца), `phase` ∈ {`down`, `move`, `up`, `cancel`}, `x`, `y`; опционально `width`, `height` (площадь пятна касания, доли экрана), `pressure` (0.0..1.0), `tool` ∈ {`finger`, `pen`} |
| `cursor_move` | абсолютно (`x`, `y`) или относительно (`dx`, `dy` в пикселях) |
| `mouse_button` | `button` ∈ {`left`, `right`, `middle`}, `down`/`up` |
| `scroll` | вертикаль в «щелчках» колеса (дробь копит ядро) |
| `scroll_h` | горизонталь в «щелчках» (наклон колеса / жест трекпада; в HID это AC Pan) |
| `key` | `usage` (USB HID usage, страница Keyboard), `down`/`up` |
| `wake` | без параметров: включить экран телефона на минуту (разблокировка вручную) |

Правила:
- **Поворот экрана и касания.** Android привязывает виртуальный тачскрин к корпусу телефона и сам поворачивает его координаты вместе с экраном (измерено на Redmi A5, Android 15). Поэтому SDK переводит координаты отображаемой картинки в координаты «по корпусу» обратным преобразованием по `rotation` из `DISPLAY_INFO`: 0°: `(x, y)`; 90°: `(1−y, x)`; 180°: `(1−x, 1−y)`; 270°: `(y, 1−x)`. Ширина и высота пятна касания при 90° и 270° меняются местами. При смене поворота активные касания отпускаются. Для мыши преобразование не нужно или не проверено (см. §12).
- `device_enable(kind, false)` снимает регистрацию устройства на телефоне (а не просто игнорирует события); перед этим всё нажатое отпускается.
- Касание ведёт себя как настоящий дигитайзер: несколько пальцев (число задаётся конфигурацией, по умолчанию 10), площадь пятна (`width`/`height`) и сила (`pressure`). Если параметр не указан, подставляется значение по умолчанию из конфигурации. В HID это Contact ID, Tip Switch, X, Y, Width, Height, Tip Pressure; Android превращает их в `ABS_MT_*` (`TOUCH_MAJOR/MINOR`, `PRESSURE`).
- Реализация HID-тачскрина: дескриптор в стиле Windows 8 (ядро `pcdock-core`, `touch_descriptor`), до 10 контактов, Report ID 1; отчёт 14 байт: `[id=1][tip][contact_id][x:u16][y:u16][w:u16][h:u16][pressure:u16][count]` (little-endian внутри HID-отчёта). Проверено на Redmi A5: режим `DIRECT`, площадь и сила доходят до приложений. Однопальцевый дескриптор Digitizer для этого не годится: Android ведёт его как тачпад.
- Положение курсора мыши телефон не сообщает: ядро оценивает его само (первый раз «прижимает» курсор к углу `(-32767, -32767)` и отсчитывает от него). Ускорение указателя Android может привести к расхождению; ядро обязано уметь пересинхронизироваться.
- Реализация HID-мыши: дескриптор Generic Desktop (ядро `pcdock-core`, `mouse_descriptor`), 3 кнопки, относительные X/Y (16 бит), колесо В + колесо Г (по 8 бит). Отчёт 7 байт: `[buttons][dx:u16][dy:u16][wheel_v][wheel_h]` (little-endian внутри HID-отчёта). Горизонталь — Consumer AC Pan (`0x0C:0x0238`): ядро Linux маппит его в `REL_HWHEEL`, дальше дело за Android (проверяется на телефоне).

## 9. Обратное давление и таймауты

- Запись из телефона в USB **блокирует** отправителя, пока хост не читает (наблюдалось до 109 с). Поэтому отправитель обязан писать из отдельного потока, а очередь видео держать в один последний кадр: старые кадры отбрасываются. Звук отбрасывается, если очередь превышает ~200 мс. `HELLO`, `PONG`, `STATUS`, `ERROR` и `DISPLAY_INFO` не отбрасываются.
- Телефон без подключённого хоста не кодирует кадры чаще раза в секунду (хранит последний кадр для шага 2 §5).
- Если от телефона нет данных 6 с и это не объясняется статичным экраном (нет `PONG`), хост может сбросить USB; приложение запускается системой только при переходе в режим аксессуара (см. `DECISIONS.md`, решение 7).

## 10. Типовая последовательность

```
Хост                         Телефон
 │── AOA handshake (§2) ───────►│  переход в режим аксессуара, система запускает приложение
 │── HELLO ────────────────────►│
 │◄──────────────────── HELLO ──│
 │◄──────────────── DISPLAY_INFO│
 │◄───────────── VIDEO_FRAME ───│  текущий экран
 │── SET_STREAM ───────────────►│
 │◄──────────────── DISPLAY_INFO│  новый размер (если изменился)
 │── PING ─────────────────────►│  каждые 2 с
 │◄──────────────────── PONG ───│
 │◄───────────── VIDEO_FRAME ───│  по мере изменений экрана
 │◄──────────── DISPLAY_INFO ───│  поворот: сначала новая информация, потом новые кадры
```

## 11. Протокол v1 (запасной режим для старых хостов)

Без заголовка и без согласования: непрерывный поток `[u32 длина, big-endian][JPEG]`. Размер берётся из JPEG. Ресинхронизация: поиск `FF D8` с отступом на 4 байта назад. Хост ничего не отправляет по потоку (ввод идёт только через HID).

Текущий viewer говорит только на v2. Телефон переходит в v1, если за 2.5 с не получил `HELLO`.

Миграция: приложение на телефоне и хост должны обновляться вместе. Хост-реализация может определять версию по первым байтам (§3).

## 12. Открытые вопросы

1. ~~**Поворот и тач.**~~ Решено: Android поворачивает координаты тачскрина вместе с экраном, SDK применяет обратное преобразование (§8). Не проверено: поведение **мыши** (относительные перемещения) при повороте и привязка тачскрина к дисплею, если у телефона несколько дисплеев.
2. **Размер экрана при поворотах.** Что делать с нестандартными размерами (складные телефоны, несколько дисплеев). Пока один дисплей.
3. **Звук.** Формат по умолчанию (PCM или Opus), задержка и синхронизация с видео (`pts_us`).
4. **H.264.** Переход с JPEG: нужны `VIDEO_CONFIG`, ключевые кадры и перезапрос после потерь.
5. **Многоточечность, площадь, сила.** Какие поля дескриптора реально доходят до приложений на HyperOS (площадь и сила), нужно ли отдельное устройство `pen` (стилус с наклоном) отдельно от `finger`.
6. **Версия AOA 1.** Если телефон поддерживает только AOA 1, HID недоступен: нужен режим «только видео» или ввод через `INPUT_*`.
7. **Идентификация.** Нужно ли подписывать или проверять хост (сейчас доверяем любому, кто прошёл handshake).
