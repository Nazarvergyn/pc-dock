# План — PC Dock / Android

Порядок — предложение, не обязательство. Статус каждого пункта: `todo` / `в работе` / `готово`.

## Направление: SDK для управления телефоном

Решено 2026-10-27. Проект становится библиотекой (SDK), а текущий `viewer` — демо-фронтендом к ней.
Позже SDK планируется использовать для тестирования игр (отдельный проект).

- **Ядро на Rust, не знает об ОС** (sans-IO): транспорт (USB, ADB) ему даёт хост. Наружу C ABI.
- **Команды от фронтенда:** движение курсора, скролл, нажатие и отпускание клавиши, палец опущен/двигается/поднят (с параметрами), включение и отключение устройств ввода.
- **События для фронтенда:** кадр экрана, звук, поворот и размер экрана, подключён/отключён.
- **Всё настраивается пользователем библиотеки:** AOA-строки (производитель, модель, описание, версия, URI, серийник), идентификаторы и дескрипторы HID, параметры стрима. Приёмник может быть чужим приложением, поэтому протокол потока публикуется как спецификация.
- **Граница библиотеки:** Android; транспорты AOA, ADB и serial под одним протоколом (решения 26, 30). Остальные платформы — отдельно.
- **Демо-фронтенд:** Python (pygame-ce) поверх C ABI, текущий `viewer` переезжает на SDK.

Порядок: (1) письменная спецификация протокола (`PROTOCOL.md`, готов черновик), (2) ядро с тестами, (3) новая версия приложения под новый протокол, включая **поворот экрана и звук** (решено делать сразу, а не после), (4) демо-фронтенд на SDK, (5) многоточечные жесты из окна, проверка площади и силы касания.

   - Проверить, как координаты HID-тачскрина и курсор мыши ведут себя в повёрнутом экране.
3. **Запись в USB в отдельном потоке** (`готово` в приложении; в адаптере ПК запись ещё в потоке `poll()`, см. `STATUS.md`): очередь из одного последнего кадра, остальные отбрасываются; сервис не зависает, когда ПК не читает.
4. **Корректное завершение демона** (`готово`, проверено частично): при выходе (закрытие окна, Ctrl+C, SIGTERM) демон снимает HID-устройства и сбрасывает USB, телефон возвращается в обычный режим за ~3 с. Если выйти в первые секунды после handshake, демон ждёт, пока телефон перейдёт в режим аксессуара, и сбрасывает его. Если сброс приходится на момент сразу после перехода в режим аксессуара, `usbipd` теряет проброс примерно на 24 с (см. `STATUS.md`).
5. **Демон как сервис на ПК** (`todo`): systemd или автозапуск при входе; для WSL — `usbipd attach --wsl --auto-attach` на оба режима телефона (по `--hardware-id`).

## Версия 1 (курс на 2026-11-10; решения 30–33)

**Ферма и настройка**

3. Plug&play: обнаружение, склейка по серийнику, `Appeared`/`State`/`Lost` — `готово` (не проверено на железе).
4. **Единая настройка в ферме** (`готово`, переименование сделано: живая — `Farm`, sans-IO — `Registry`): `FarmConfig` (обнаружение, семейства, исключения, закреплённые телефоны, поток по умолчанию), фабрика каналов и разбор `usb:…`/`adb:…` переезжают из `pcdockd` в ферму; закреплённые телефоны получают те же состояния и события; `--auto` и `--phone` сочетаются; демон только превращает аргументы в `FarmConfig`.

## Идеи без решения

- **Root-бэкенд** (идея, для отдельной библиотеки, не для этой): на рутованном телефоне серверный процесс запускается от root (`su`), диалог записи экрана и отладка по USB не нужны. Захват экрана напрямую, виртуальный ввод через `/dev/uinput`, связь через тот же USB. Требует root, с которым часть банковских и защищённых приложений не работает, поэтому только опционально.

- Резервный захват через ADB: **не входит в эту библиотеку** (она только про Android и AOA). Если понадобится, это отдельная библиотека (см. `DECISIONS.md`, решения 9 и 11).
